Redis 单线程模型：一条 GET 命令从 epoll 到回复的完整路径

创建 2026 年 11 月 22 日 更新 2026 年 11 月 22 日 约 3 分钟 Redisepoll单线程性能

「Redis 是单线程的」这句话只对了一半：处理命令是单线程，但网络读写、持久化、集群通信都有别的线程。搞不清这个边界，就会出现「我用了 6.0 的 io-threads，怎么还是被一个大 key 卡住」的疑问。

一条 GET 的完整路径

客户端发来 GET user:1，服务端经历的步骤是：

epoll_wait 返回可读事件
   ↓
读 socket，解析 RESP 协议（*2\r\n$3\r\nGET\r\n$6\r\nuser:1\r\n）
   ↓
按命令名查命令表，拿到 redisCommand 和参数个数
   ↓
校验参数、权限、内存上限、是否处于阻塞状态
   ↓
调用 getCommand：在 dict 里查 key，命中就返回 robj
   ↓
写回 socket（先塞进输出缓冲区，由事件循环负责写出去）

这整段除了读写 socket，都在同一个主线程里串行完成。所以「单线程」准确的说法是：命令的执行是串行的，一条命令执行期间，别的命令连解析的机会都没有。

为什么单线程还能快

三个原因，按重要性排：

  1. 全内存操作：一次 hash 查找是 O(1)，耗时在几十纳秒量级，瓶颈根本不在 CPU
  2. 无锁无竞争：不需要加锁，也就没有锁开销和上下文切换
  3. IO 多路复用：一个线程用 epoll 同时盯着上万个连接，不需要每连接一线程

瓶颈在网络和内存带宽，不在计算。所以「多线程能更快」这个直觉在 Redis 上不成立——加线程反而要处理并发访问共享数据结构的锁。

事件循环长什么样

aeEventLoop 一轮循环做三件事：

while (!stop) {
    // 1. 计算距离下一个定时任务还有多久，作为 epoll_wait 的超时
    timeout = 最近的时间事件 - now;
    // 2. 等文件事件（客户端可读/可写）
    numevents = epoll_wait(epfd, events, maxevents, timeout);
    // 3. 处理文件事件：读命令、执行、写回复
    for (i = 0; i < numevents; i++) handleFileEvent(events[i]);
    // 4. 处理时间事件：serverCron（过期清理、持久化触发、集群心跳等）
    processTimeEvents();
}

注意第 1 步：超时时间由最近的时间事件决定。如果有个定时任务 100ms 后要跑，epoll_wait 最多等 100ms 就得回来。这也是为什么单线程的 Redis 仍然能定期做后台任务——它不是靠别的线程，而是靠「等 IO 的时候顺便看时间」。

6.0 的 IO 多线程分担了什么

配置长这样：

io-threads 4
io-threads-do-reads yes

它只做两件事：读 socket + 解析协议、写 socket。命令的执行依然在主线程串行。

流程变成：

多个 IO 线程并行读 + 解析 → 主线程串行执行所有命令 → 多个 IO 线程并行写回

所以 io-threads 的效果取决于「单条命令是否够小、并发是否够高」：命令都很轻时，瓶颈在网络 IO，加线程有效；一旦有慢命令（大 key、KEYS、复杂 Lua），主线程照样被卡，加多少 IO 线程都没用。

哪些操作会卡住整个实例

这是最该记住的部分。以下操作在主线程里同步完成，执行期间所有其他请求排队：

操作 为什么慢 替代方案
KEYS * 全库遍历，O(N) SCAN 游标分批
DEL 大集合 逐个释放元素内存，O(N) UNLINK（异步释放）
FLUSHALL / FLUSHDB 同上，还带同步 加 ASYNC 参数
HGETALL 大 hash 一次性构造回复，内存翻倍 HSCAN 分批
复杂 Lua 脚本 整个脚本原子执行 拆分，控制执行时间

还有一个容易被忽略的：大 key 的序列化。一个有 100 万元素的 zset，即使只做 ZRANGE key 0 9，命令本身不慢，但如果这个 key 正好在做 RDB 持久化或主从全量同步，fork 出来的子进程要复制页表，主线程也可能被拖慢。

慢查询日志不记录排队时间

SLOWLOG 记录的是命令执行时间，不含网络排队、不含等前一条命令执行完的时间。所以出现「客户端感觉慢，但慢日志里什么都没有」时，八成是这两类原因：

  1. 前面有慢命令在排队（看 LATENCY 和 INFO commandstats）
  2. 网络往返或客户端连接池打满

排查顺序建议是：先看 INFO latencystats 有没有异常高的命令，再看 SLOWLOG GET 10，最后才怀疑网络。

小结

  • 单线程指的是命令执行串行，读写 socket 在 6.0 之后可以多线程
  • 快的原因是内存操作 + 无锁 + IO 多路复用，不是「单线程更快」
  • 事件循环的超时由最近的定时任务决定，所以单线程也能跑后台任务
  • 卡顿几乎都来自 O(N) 命令和大 key，io-threads 救不了这类问题
  • 慢日志不含排队时间，客户端变慢时先怀疑前面有慢命令

判断一个操作会不会阻塞，只需要问一句：它是 O(1) 还是 O(N)？ O(N) 的命令在数据量大时一定要换成分批版本。
