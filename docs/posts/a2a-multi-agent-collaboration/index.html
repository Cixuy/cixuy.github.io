从 MCP 到 A2A：多 Agent 协作到底难在哪

创建 2026 年 11 月 16 日 更新 2026 年 11 月 16 日 约 4 分钟 专栏 · A2A 与多 Agent 协作（1 章） A2AMCP多智能体Go

A2A 与多 Agent 协作 第 1 / 1 章

  1. 01从 MCP 到 A2A：多 Agent 协作到底难在哪

MCP 那套做完之后，我一直有个疑问：既然每个 Agent 都能调工具了，为什么还需要 A2A？

直到把「企业 IT 服务台」这个场景写了一遍才明白——MCP 解决的是"一个 Agent 内部怎么用工具"，A2A 解决的是"多个 Agent 之间怎么交接任务"。前者是纵向的，后者是横向的，两者不冲突，也互相替代不了。

先把边界划清楚

员工报一句"打印机连不上"，现实里的处理链路是这样的：

  1. 先判断是设备问题还是流程问题
  2. 是设备问题就去看队列、驱动、网络——这需要监控数据
  3. 知道根因之后再去手册里找处置步骤
  4. 处理不了就建单，带 SLA

四步里每一步的知识边界都不一样。硬塞给一个大模型，它答不准也没人担责；拆成几个专职 Agent，每个都小而准，但谁来分派、谁能调谁、出事怎么查就成了新问题。

这就是 A2A 的位置。它不管 Agent 内部怎么思考，只管一件事：A 能不能把任务交给 B，并且知道 B 干完了没有、干出了什么。

A2A 的三个核心概念

Agent Card：每个 Agent 暴露一张名片，在 /.well-known/agent-card.json。写清楚自己叫什么、会哪些技能、支持什么输入输出模态。网关启动时拉一遍名片就完成注册，不需要额外的注册中心。

Task：任务是一次协作的载体，有 ID、有状态机（submitted → working → completed / failed / canceled）、有 history、有 artifacts。跟 HTTP 请求最大的区别是任务是有生命周期的，可以查询、可以取消、可以中途汇报进度。

SSE 流式：任务状态变化通过 text/event-stream 推给调用方，而不是让调用方轮询。多跳转发时这一层最容易出问题——上游断开、下游还在跑，任务状态就悬在中间。

协议一天能写完，治理要一周

第一版我按规范把 JSON-RPC 的 message/send、tasks/get、tasks/cancel 和 SSE 都实现了，跑通"一句话两跳"只用了半天。剩下的时间全花在这几件事上：

幂等。用户在弱网下点两次发送，不能建两张工单。做法是拿 messageId 做幂等键，映射到 taskId；索引跟任务一起落盘，重启后依然生效。这里有个细节：幂等要在建任务之前判断，不是执行完之后返回旧结果——否则两次并发请求还是会各跑一遍。

配额。一个 Agent 被上游疯狂调用，会把后面的任务全堵死。给每个 Agent 独立令牌桶，超额直接拒绝，并在审计里标 rejected。注意配额拒绝不该重试，重试只会把压力再送一遍。

部分降级。两跳里第二跳失败了，任务不能整体标失败——第一跳的诊断结论是有价值的。现在的做法是标"部分降级完成"，附一句"结论仅基于成功的那一跳"，让调用方自己判断够不够用。

落盘与恢复。任务状态每变一次就原子写一次（写 .tmp 再 rename），带 80ms 防抖。演示时直接 kill 掉进程再重启，任务和幂等索引都还在——这一条比任何性能数字都有说服力，因为它证明的是"这套东西敢上生产"。

审计。每次跨 Agent 调用记一条 hop：谁调的、哪个技能、耗时多少、第几次尝试、产出是什么。界面上渲染成瀑布图。企业采购看的就是这一条——出事能不能查。

三个真实的坑

监听地址写成 URL。card.URL 是 http://127.0.0.1:18091，我直接塞给了 http.Server{Addr: ...}，三个下游全部静默失败，注册表空得像没写代码。错误被 ListenAndServe 的返回值吞掉了，因为我在 goroutine 里没处理它。

JSON-RPC 的 result 用了 any。解析下游响应时我写 rpc.Result.(json.RawMessage)，但 encoding/json 解到 any 里是 map[string]any，断言直接 panic——而且是在任务 goroutine 里 panic，把整个网关带走了。修法是字段类型改成 json.RawMessage，另外给任务 goroutine 加 recover，一个任务出错不该影响服务。

前端 hops 是 null。Go 里 nil slice 序列化成 null 而不是 []，前端 null.map() 直接报错。这类问题不加防护就会在"空数据"这个最不该崩的场景崩掉。

实测

场景 结果
设备类报障 两跳：诊断 157ms + 知识库 95ms，返回两份产出
账号类报障 两跳：知识库 + 工单，自动建单，SLA 4 小时
同一 messageId 重复提交 幂等命中，返回同一 taskId，未重复执行
SSE 订阅 依次收到 working ×5 → completed
进程 kill 后重启 3 条任务全部恢复，幂等索引仍生效

还没做的

  • 注册准入：现在是"知道地址就能注册"，生产环境要防能力声明造假（自称会诊断，其实乱答）
  • 按 Agent 熔断：连续失败应该自动摘除一段时间，现在只会一跳一跳地失败
  • 多实例：单机部署没问题，多网关实例要加分布式锁，否则同一任务会被跑两遍
  • trace 回放：现在能看到每跳耗时，但不能重跑某一跳做对比

一句话总结

A2A 的价值不在协议本身——协议一天就能实现完。它的价值是把"多个 Agent 协作"从一堆口头约定，变成了可发现、可治理、可审计的工程问题。而这三件事，恰恰是 demo 和生产的分界线。
