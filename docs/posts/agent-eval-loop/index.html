前五章改了很多东西：切片大小、召回条数、记忆注入、合并规则。每一次改完，我都拿同一段代码试一遍，看输出，觉得"这次明显更准了"。

问题在于我每次都拿同一段代码试。那段代码我太熟了，知道它有哪些问题，潜意识里就会往"这次报全了"的方向判。

真正的转折是第三次改切片：从 1200 字改到 800 字，手感上更准，实际是把一个跨函数的上下文切断了，模型再也拼不出完整链路。

评测集不是测试集

一开始我想写单元测试，很快发现不对：评审结果不是布尔值，没有"正确/错误"这种判断。同一条问题，描述不同、位置差一行，都可能是合理的。

所以评测集是带标注的样例，不是断言：

case-01  空指针未判空          → 期望命中，位置 12-14 行
case-02  资源申请未释放        → 期望命中，位置 30 行
case-03  命名不规范            → 期望命中，位置 8 行
case-04  格式良好但风格老旧的代码 → 期望不报（负样本）
case-05  单行 if 省略花括号     → 期望不报（已知误报，靠记忆压掉）

核心是有了负样本。只准备"应该报的问题"会让指标永远向上——加点规则就多命中几条，看起来一直在进步。

我现在的集子里正负样本大概 2:1。负样本里最有用的是两类：已经修好但长得像坏代码的，和历史上误报过的。

三个指标，只看两个

指标 定义 用途
召回 标注的问题被报出来的比例 主指标
误报率 报出来但不在标注里的条数 / 总条数 主指标
位置准确率 行号落在标注范围内的比例 参考

前两个看趋势，第三个只在明显下滑时查。行号差一两行通常是可接受的，为它优化会带偏整个规则设计。

有个必须一起记录的东西：耗时。加了记忆注入和两轮检索之后，单次评审从 1.2 秒涨到了 3 秒多。召回涨了两个点，但交互上明显变卡。这种权衡只能靠数据摆出来，靠手感永远是"再准一点更好"。

怎么跑

不搭平台，一个脚本就够：

python eval/run.py --cases eval/cases --out eval/runs/2026-11-16.json

每个 case 是一段代码 + 一份 JSON 标注。跑完把结果写成一行摘要，追加到 eval/history.md：

2026-11-16  chunk=800  mem=on   召回 0.86  误报 0.11  平均 3.1s
2026-11-14  chunk=1200 mem=on   召回 0.79  误报 0.09  平均 2.2s
2026-11-12  chunk=800  mem=off  召回 0.83  误报 0.18  平均 2.9s

这张表比任何一次"我觉得更准了"都有说服力。翻回去看，记忆注入的收益（误报从 0.18 降到 0.11）其实比切片调整大得多，而我当时的直觉是反过来的。

评测最容易骗自己的三件事

一次只改一个变量。 我干过同时改切片和召回条数，结果指标掉了，完全不知道是谁的责任。现在改之前先把当前状态记录一条基线。

不要用改过的用例。 发现某条没报，就把标注补上——这叫对着答案改卷子。用例只在"这条标注本身错了"的时候才动，且要单独记一笔原因。

注意缓存。 检索有缓存、工具结果有缓存，第二次跑同一个 case 会快很多也"准"很多（因为命中了上一次的缓存）。跑评测前必须清缓存，否则数字没有可比性。

六章写完了

回头看这个系列，六章其实是六个"我以为很简单"：

  1. 以为 Agent 是框架问题，其实是循环和工具设计
  2. 以为接协议是加依赖，其实是版本冲突和序列化层
  3. 以为切片是调参数，其实决定了模型能看到什么因果
  4. 以为记忆是向量库，其实是分层和过期治理
  5. 以为容错是 try-catch，其实是给模型保留决策权
  6. 以为评测要写测试，其实是攒带标注的样本

这个项目还在改。下一个想动的是把检索的相似度阈值做成可配置的，现在硬编码在里面，调一次要重新打包——又是一件"看起来很简单"的事。
