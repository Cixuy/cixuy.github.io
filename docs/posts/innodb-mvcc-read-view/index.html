InnoDB 的 MVCC：可重复读下的一条 SELECT 是怎么拿到快照的

创建 2026 年 11 月 20 日 更新 2026 年 11 月 20 日 约 4 分钟 MySQLInnoDBMVCC事务

同一个事务里查两次，结果一样，但中间另一个事务明明已经提交了——这件事在 MySQL 里叫可重复读，实现它的机制叫 MVCC（多版本并发控制）。

大多数人能背出「MVCC 靠 undo log 和 Read View 实现」，但真被追问「Read View 里有什么」「RC 和 RR 差在哪一行代码」的时候会卡住。这篇按一条 SELECT 的执行路径走一遍。

一行数据其实有三个隐藏列

建表时只写了业务字段，InnoDB 在行上还偷偷加了三个：

隐藏列 长度 作用
DB_TRX_ID 6 字节 最后一次修改这行的事务 ID
DB_ROLL_PTR 7 字节 指向 undo log 里这行的上一个版本
DB_ROW_ID 6 字节 没有主键时用，有主键就不需要

关键在 DB_ROLL_PTR：每次更新不是原地改，而是把旧值写进 undo log，然后让新版本的 roll_ptr 指向旧版本。于是同一行数据变成一条版本链：

当前行(trx_id=105) ──roll_ptr──▶ undo(trx_id=101) ──roll_ptr──▶ undo(trx_id=98) ──▶ null

一条 SELECT 想读到「应该看见的那个版本」，就得沿着这条链往回走，直到找到一个对当前事务可见的 trx_id。

Read View 里到底有四个什么

判断可见性靠的不只是自己的事务 ID，而是一个快照结构：

字段 含义
m_ids 生成快照那一刻，所有活跃（未提交）事务的 ID 列表
min_trx_id m_ids 里的最小值
max_trx_id 系统下一个要分配的事务 ID（注意不是 m_ids 最大值 + 1）
creator_trx_id 创建这个快照的事务自己

可见性判断就是四句话：

  1. trx_id == creator_trx_id → 自己改的，可见
  2. trx_id < min_trx_id → 这事务在我快照之前就提交完了，可见
  3. trx_id >= max_trx_id → 这事务在我快照之后才开始，不可见
  4. 落在中间 → 看它在不在 m_ids 里：在（当时还活着）→ 不可见；不在（当时已提交）→ 可见

不可见就顺着 roll_ptr 往回找下一个版本，重复上面四步，直到找到可见版本或者链走完。

RC 和 RR 只差一行

两个隔离级别用的是同一套版本链和同一套判断逻辑，唯一的区别是Read View 什么时候生成：

  • 读已提交（RC）：每条 SELECT 都生成一个新的 Read View
  • 可重复读（RR）：只在事务里第一次快照读时生成，之后整个事务复用这一个

所以 RR 下你看到的是「第一次查询那一刻」的世界，而不是「BEGIN 那一刻」的世界。这个细节很容易错：

-- 事务 A
BEGIN;
SELECT * FROM t WHERE id = 1;   -- 这一刻生成 Read View，假设读到 v1
-- （事务 B 更新并提交）
SELECT * FROM t WHERE id = 1;   -- 还是 v1，因为复用同一个 Read View
COMMIT;

如果把中间那条 SELECT 去掉，事务 A 直接 B 更新后再查，读到的是新值——因为 Read View 是在后面那次查询才生成的。很多「RR 好像没生效」的疑惑都是这个原因：快照不是跟着 BEGIN 走的。

快照读和当前读是两套逻辑

MVCC 只服务于快照读，也就是普通的 SELECT。下面这些是当前读，一律读最新已提交版本，并且加锁：

SELECT ... FOR UPDATE;        -- 加排他锁
SELECT ... LOCK IN SHARE MODE; -- 加共享锁
UPDATE / DELETE / INSERT;     -- 天然是当前读

这也解释了幻读为什么有两种表现：

  • 快照读下，MVCC 让你看不见别人新插入的行，所以「幻读」被规避了
  • 当前读下（比如 FOR UPDATE 范围查），必须靠 next-key lock（记录锁 + 间隙锁）阻止别人往间隙里插，否则同一事务两次当前读会多出行来

所以「RR 能防幻读」这句话要加限定：快照读靠 MVCC，当前读靠间隙锁。少了后半句，遇到 FOR UPDATE 就会翻车。

三个实际踩过的坑

一、长事务会让 undo 一直涨。 版本链上的旧版本什么时候能删？当没有任何 Read View 还需要它的时候。一个开了十分钟没提交的事务，会让这十分钟内所有被改过的行的旧版本都留着，undo 表空间暴涨，同时所有查询都要走更长的版本链。线上看到 undo 持续增长，先查 information_schema.innodb_trx 里的长事务。

二、SELECT ... FOR UPDATE 在 RR 下锁的范围比想象大。 RR 下没有索引的更新会锁全表（更准确说是锁所有扫描到的行加间隙），一条 UPDATE t SET x=1 WHERE name='a'（name 无索引）能把整张表锁住。这不是 MVCC 的问题，是当前读加锁的问题，但现象常常混在一起。

三、MVCC 不解决写写冲突。 两个事务同时 UPDATE 同一行，后到的那个会阻塞等锁，等前一个提交后它读到的是最新版本再改（这叫当前读），不存在「基于旧版本覆盖」的情况。所以「MVCC 让读写不阻塞」是对的，「MVCC 让写写不阻塞」是错的。

小结

一条 SELECT 在 RR 下的完整路径是：

  1. 用本事务第一次快照读时生成的 Read View 作为判据
  2. 拿到行上最新的 DB_TRX_ID，按四个字段判断可见性
  3. 不可见就沿 DB_ROLL_PTR 回溯 undo 版本链，直到找到可见版本
  4. 如果语句是当前读（FOR UPDATE / 更新删除），跳过 MVCC 直接读最新版本并加锁

记住两句话就够了：RR 的快照在第一次读时生成，不在 BEGIN 时；MVCC 只管快照读，写写冲突和当前读还得靠锁。
