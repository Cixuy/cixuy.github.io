上下文窗口不是无限口袋：8000 字符预算怎么切

第一次跑评审，我把整个文件贴进 prompt 里。两百多行的 Java 文件，加上规则说明和输出格式要求，总共一万多字，模型跑得动，结论也对。

换成真实项目里的八百行文件，问题全出来了：前面说的"只报严重级别 error"被忽略，输出格式从 JSON 变成了解释性段落，还有几处引用了文件里根本不存在的行号。

不是模型变笨了，是上下文被撑满之后的必然结果：模型对 prompt 里越靠前、越结构化的内容注意力越强，塞到后面就被稀释了。

先把预算说清楚

我把一次请求的上下文预算定在 8000 字符，切分单位 800 字符。这两个数的来历：

  • 8000：模型能给到的稳定注意力区间远大于这个数，但我要留出空间给工具返回、历史轮次和系统提示。实测超过 8000 之后，指令遵循开始不稳定
  • 800：一段 800 字符的代码大约 20-30 行，通常是一个完整方法。再大就会出现"一个片段里两件事"，检索和引用都变糊

这两个数不是调优出来的最优解，是"能稳定跑住"的起点。第三章末尾我会说为什么后来把它们做成可配置的。

切分不能按字数硬切

按 800 字硬切最省事，也最坑：切点落在方法中间，模型看到半截 if，会自己补一个不存在的 } 然后开始瞎解释。

我的切分顺序是：

  1. 按空行切块，尽量保持方法/类的边界
  2. 单块超过 800 就往下找最近的 } 或空行断点
  3. 相邻块之间保留 1 行重叠，避免边界处语义断裂
  4. 每块记录起止行号

第 4 条是为了引用。模型说"第 12 行有问题"时，我得能验证这个行号确实在送进去的片段里，否则就是幻觉。

预算超了砍谁

一个八百行的文件切完是二十多块，全塞就是一万六千字，超一倍。必须选。

我的优先级：

顺序 内容 理由
1 变更的文件（diff 部分） 评审的重点就是这次改了什么
2 被调用方签名 判断参数合法性必须看
3 同文件相关片段 上下文连贯性
4 历史问题召回 有证据价值但可省
5 整个文件的其他片段 最后才考虑

一开始我把整个文件排在第 2 位，觉得"看得全才准"，结果每次都把预算吃光，历史召回一条都塞不进去，模型也就永远说不出"这个问题历史上出现过"。

改成按 diff 优先之后，同样的预算下结论质量明显更好——因为模型看到的是"改动 + 相关上下文"，而不是"一个完整但无关的巨文件"。

砍掉的部分要告诉模型

这是最容易漏的一步。预算不够只送了 60% 的代码，如果不说明，模型会默认自己看到了全部，然后断言"这个类没有其他调用方"。

所以每次裁剪完，我在系统提示里追加一段：

[上下文说明]
本次只提供了 12/21 个代码片段（按 diff 与调用关系优先）。
未提供的部分可能包含其他调用点，涉及"是否全部覆盖"的结论时请说明依据。

加了这段之后，模型开始主动说"仅基于提供的片段"，而不是给绝对结论。评审工具最怕的就是这种过度自信。

工具返回也要算预算

这点我前面提过，这里补一个数字：一次 search_similar 召回 8 段、每段 1000 字，就是 8000 字符——一次性把整轮预算吃光，后面所有工具调用都塞不进去。

现在的返回格式是每段 200 字 + 相似度 + 片段 ID，8 段总共 1600 字符左右，占预算 20%。想看全文再用 ID 单独取。

原则很简单：工具返回给的是索引，不是全文。 让模型自己决定展开哪个。

反思

做完这一章我才意识到，上下文预算不是一个"技术参数"，而是一个产品决策：你决定让模型优先看到什么，就等于决定了它能得出什么结论。

后来我把 800 / 8000 都提成了配置项（一开始是硬编码），因为不同项目差别很大：三千行的老项目需要更激进的裁剪，几百行的小工具反而可以给全。下一章写另一件事——怎么让 Agent 记住这些偏好，而不是每次都重新告诉它。
