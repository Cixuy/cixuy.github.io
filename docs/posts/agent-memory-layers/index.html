让 Agent 记住这个项目：记忆分三层，别混成一层

"记忆"这个词很容易把人带偏。一开始我以为记忆是一个向量库，把聊天记录全塞进去，下次全捞出来——结果捞出来的东西一半是废话，另一半和当前问题无关，纯占上下文。

做下来发现记忆至少要分成三层，每层的生命周期、存储、注入方式都不一样，混在一起就没法维护。

三层记忆

层 生命周期 存哪里 干什么
会话记忆 一次对话 内存里的 messages 让模型知道自己刚做过什么
项目记忆 长期，可人工修改 MySQL 一行一条 记住这个项目的偏好和结论
证据（检索） 只读，随时可重建 向量库 回答"为什么"时引用的原文

会话记忆不用设计，就是循环里的消息数组。真正需要设计的是后两层——而它俩最容易被混成一个向量库。

一句话区分：项目记忆是结论，检索是证据。

"这个项目不用 camelCase 命名"是结论，应该被直接遵守，不需要每次重新推。"9 月 12 日有个同类问题，当时改成下划线了"是证据，只在该用的时候被召回。

项目记忆长什么样

不是聊天记录，是一行一行的结构化条目：

project_id | key              | value                        | enabled | updated_at
cra        | ignore_rule      | 命名规范检查                  | 1       | 2026-10-08
cra        | style            | 指标计算用 snake_case         | 1       | 2026-10-11
cra        | known_issue      | 第 3 段正则误报 if 单行省略    | 1       | 2026-10-19

几个刻意的设计：

key 是枚举，不是自由文本。 如果让模型随便写 key，三个月后你会得到 40 个含义重叠的键，清理比重写还贵。我定了三类：忽略规则、风格约定、已知误报，超出的直接拒绝写入。

写入必须走工具，且带理由。 模型调 set_memory 时要求同时给 reason，理由为空就写不进去。这条约束压掉了很多"顺手记一下"的噪声。

enabled 是给人看的。 用户发现某条记忆不适用，可以在界面上关掉而不是删除。关掉的条目还在库里，方便回溯"为什么会得出这个结论"。

怎么注入

不是全量塞进 system prompt。我的做法是：

  1. 按 key 分组，每组最多取最近 3 条，总数不超过 12 条
  2. 按当前请求涉及的文件路径做一次粗筛（known_issue 里带路径的优先）
  3. 拼成一小段结构化文本，不写成自然语言
[项目约定]
- 命名规范检查：已忽略（用户 2026-10-08 确认）
- 指标计算：使用 snake_case
[已知误报]
- if 单行省略：第 3 段正则会误报，不要重复报告

自然语言写法的记忆最坑。模型会把"用户说过可能不用检查命名"理解成"有时要检查"，然后随机执行。结构化短句没有解释空间。

过期是最大的坑

记忆写进去容易，失效没人管。真实碰到两次：

第一次：忽略了"命名规范检查"，两周后代码重构完，命名都改好了，这条记忆还在，新代码里的命名问题全被吞掉了。

第二次：记了"第 3 段正则会误报"，我把正则修好之后忘了删，等于给错误开了永久豁免。

后来加了两个机制：

  • 每条记忆带 updated_at，超过 30 天在注入时追加一句"该约定已 32 天未确认，如已不适用请关闭"
  • known_issue 类的记忆，规则代码变更时（用文件 hash 判断）自动标记为"待复核"，不再默认注入

第二个机制有点像给记忆加了个 TTL，但触发条件是代码变更而不是时间——对设计类项目更准。

记忆和检索的边界

有个细节值得单独说：检索到的内容不写回记忆。

早期版本里，模型查到一条"历史上有同类问题"，会顺手调 set_memory 记下来。结果库里堆满了检索结果的副本，第三次评审时召回的全是自己抄自己的结论，形成回音室。

现在的规矩是：检索结果只作为这一轮的上下文，会话结束就没了；要沉淀成记忆，得由人确认，或者在界面上点一下"记住这条"。

写入口收窄之后，记忆条数从两百多条降到了二十几条，但每条都能用。
