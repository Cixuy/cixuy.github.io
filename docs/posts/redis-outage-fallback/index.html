Redis 整体不可用时的降级与限流：一次故障演练复盘

做完缓存治理之后，我做了一次演练：直接把 Redis 进程 kill 掉，看系统会怎么样。

结果是接口大面积超时，数据库连接池在 40 秒内被打满，然后整个服务不可用。Redis 挂了两分钟，系统崩了六分钟 —— 因为数据库被打到需要时间缓过来。

这次演练之后我才意识到：缓存不只是提速，它同时承担了削峰。挂掉的时候，那部分流量不会消失，会原封不动地砸到数据库上。

三层防护

第一层：连接超时必须短

默认的 Redis 客户端超时往往是秒级甚至无限。Redis 挂掉时，请求不是"快速失败"，而是"卡在那里等" —— 线程被占住，比报错更糟。

spring:
  data:
    redis:
      timeout: 500ms
      connect-timeout: 200ms
      lettuce:
        pool:
          max-active: 16
          max-wait: 200ms

三个数字的含义：连接 200ms 建不上就算失败、命令 500ms 没回就放弃、池子满了等 200ms 拿不到连接就抛异常。全部是"快速失败"的取向，宁可报错也不占线程。

这一步改完再演练，接口从"卡死"变成了"快速报错"，但用户看到的是 500 —— 还得往下做。

第二层：降级 + 限流

降级很简单，就是 try-catch 后直接查库：

public DeviceStatus getStatus(Long id) {
    try {
        DeviceStatus cached = redis.get(key(id));
        if (cached != null) return cached;
    } catch (Exception e) {
        log.warn("redis unavailable, fallback to db, key={}", key(id), e);
    }
    return loadFromDb(id);
}

但只做降级等于把数据库送上去挨打。缓存平时挡住的那 90% 流量现在全落下来，DB 必死。

所以降级必须配限流。我用的是最简单的方案 —— 信号量控制同时打到 DB 的请求数：

private final Semaphore dbPermit = new Semaphore(20);  // 按连接池大小定

public DeviceStatus loadFromDb(Long id) {
    if (!dbPermit.tryAcquire()) {
        throw new ServiceBusyException("系统繁忙，请稍后重试");
    }
    try {
        return mapper.selectById(id);
    } finally {
        dbPermit.release();
    }
}

多出来的请求直接返回"系统繁忙"，用户体验不好，但至少系统还活着。这比全站 500 好得多。

限流阈值怎么定？看数据库连接池大小 —— 池子 20 个连接，信号量就给 15～18，留几个给非缓存路径的请求（写操作、定时任务）。

第三层：二级缓存兜底

Redis 整体不可用时，本地缓存能挡住一部分。我用 Caffeine 存了最热的几个字典（权限、设备类型），有效期 5 分钟。

多层缓存有个必须处理的问题：一致性。本地缓存的更新是个麻烦事 —— 多实例部署时，A 机器改了数据，B 机器的本地缓存还是旧的。

我的取舍是：本地缓存只放变化极少的数据（字典表、配置项），并且只在一级缓存不可用时才启用。正常状态下本地缓存不参与读路径，避免一致性问题；Redis 挂了它才顶上，这时候"数据可能旧 5 分钟"完全可以接受。

演练怎么做

改完之后要验证，方法是模拟真实故障，不是改配置。

# 方式一：直接杀掉 Redis（最真实）
redis-cli shutdown nosave

# 方式二：不断开连接但让命令超时（模拟网络问题）
# Linux 上用 tc 加延迟，Windows 上可以直接停服务

然后观察三个指标：

  1. 接口响应时间 —— 应该从"秒级卡死"变成"快速失败"
  2. 数据库连接池活跃数 —— 不应该打满
  3. 错误率 —— 会上升，但要可控，不能是 100%

我第一轮演练的数据库连接池活跃数是 20/20（打满），第二轮降到 12/20 左右。这个数字是判断降级有没有生效最直接的依据。

一个反面教训

我一开始的做法是捕获所有异常后静默降级，日志只打 debug 级别。结果 Redis 挂了两小时没人发现 —— 系统看起来"正常"，只是慢了一点，数据库压力大了一点。

后来加了三条告警：

  • Redis 连接失败连续 10 次 → 告警
  • 降级路径被触发超过 100 次/分钟 → 告警
  • 数据库连接池活跃数 > 80% 持续 1 分钟 → 告警

降级是为了让系统活着，不是为了掩盖故障。 这两件事很容易混在一起。

小结

缓存高可用这件事，思路和缓存击穿是相反的：

  • 击穿是个别 key 失效，要保证"有且只有一个请求去加载"
  • 整体不可用是所有 key 失效，要保证"大部分请求根本不去加载"

前者靠锁，后者靠限流。两者的共同点是：都不能让流量原样穿透到数据库。

最后留一个问题给自己：如果数据库也挂了呢？答案是没有答案 —— 到那一层只能靠多副本和主从切换，那是运维的事，不是代码能兜住的。所以降级的目标不是"永不宕机"，是把故障控制在 Redis 这一层，不要让数据库跟着倒。
