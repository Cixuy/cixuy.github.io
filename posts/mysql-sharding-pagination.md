ServerOps 里操作日志涨得最快，一个月就过了千万。按时间分表（`op_log_202608`、`op_log_202609`……）之后写入压力下来了，但后台的日志列表页挂了。

原因很直接：原来一句 `SELECT * FROM op_log ORDER BY create_time DESC LIMIT 20` 解决的事，现在要跨十几张表。

## 三个具体问题

**1. 分页怎么翻。** `LIMIT offset, size` 在单表里就是跳过 offset 行，跨表就没法这么写 —— 每个表的 offset 分布不一样。

**2. 总数怎么算。** 前端要显示"共 N 条"。单表 `COUNT(*)` 已经是全表扫，跨十几张表就是十几倍。

**3. 排序怎么做。** 需要按时间倒序取最新 20 条，得从每张表各取 20 条再归并，不能只查最后一张表（虽然理论上最新数据都在最新的表里，但表边界附近会有跨表的情况）。

## 方案一：并行查询 + 内存归并

适合**浅分页**（前几十页）。

思路：每张表都按同样的条件查 `LIMIT 0, offset+size`，然后在内存里归并排序，最后截取目标区间。

```java
// 每张表各取前 (offset + size) 条，线程池并行
List<Log> merged = tables.parallelStream()
    .map(t -> query(t, orderByTimeDesc, offset + size))
    .flatMap(List::stream)
    .sorted(comparing(Log::getCreateTime).reversed())
    .skip(offset)
    .limit(size)
    .collect(toList());
```

代价很明确：**表越多、翻得越深，代价越大**。翻到第 10 页，每张表都要扫 200 行，20 张表就是 4000 行。所以这个方案只适合"用户不会翻太深"的场景，我给它加了硬限制：只允许翻前 50 页。

数量统计单独处理 —— 用每张表的 `COUNT(*)` 累加，但**加缓存**，缓存 5 分钟。管理员看到的总数是"5 分钟前的"，这个精度对日志列表完全够用。

## 方案二：游标分页（seek method）

适合**无限滚动**，也是我现在用的方式。

不分页，改成"从哪一条之后继续取"：

```sql
SELECT * FROM op_log_202608
WHERE (create_time, id) < ('2026-11-14 10:00:00', 1024)
ORDER BY create_time DESC, id DESC
LIMIT 20;
```

用 `(create_time, id)` 做联合游标，是因为同一秒可能有多条日志，只用时间会漏数据或者重复。加 `id` 保证唯一。

好处是**翻到第几页都是同样的代价**，不随 offset 增长。坏处是**不能跳到第 7 页** —— 前端交互要改成"加载更多"。

管理后台这个改动我跟产品争了两句，最后他接受了：日志这种数据，用户实际行为就是"看最新的"或者"按条件搜"，没人真的点到第 30 页。

## 方案三：单独建一张索引表

适合**真的需要任意翻页 + 复杂筛选**的场景。

把查询条件需要的字段（时间、操作人、模块、结果）单独维护到一张不分表的宽表里，分页在宽表上做，拿到 id 再回各分表取详情。

代价是要维护两份数据，写入时多一次同步。**如果你的筛选条件很复杂，这是唯一能撑住的方案**；但简单场景下不值得。

## 我最后怎么选的

按场景拆开，不追求一个方案打天下：

| 场景 | 方案 |
|---|---|
| 日志列表（默认查看） | 游标分页，只提供"加载更多" |
| 按时间段/操作人筛选 | 游标分页 + 索引表辅助 |
| 总数统计 | `COUNT(*)` 累加 + 5 分钟缓存 |
| 导出 Excel | 异步任务，逐表读取写文件，不走分页 |

导出那条特别说一下：原来是想复用列表的查询逻辑，结果导出 5 万条时直接 OOM。改成异步任务后，每张表读完就写一行到文件、清空集合，内存占用是平的。

## 几个容易忽略的细节

**表名要参数化。** 分表后最常见的写法是字符串拼表名，`"op_log_" + month`。这既是 SQL 注入的口子，也让预编译失效。我的做法是表名从一个白名单枚举里取，拼之前校验格式必须是 `op_log_\d{6}`。

**分表键要和查询条件对齐。** 如果 90% 的查询都带时间范围，按时间分表是对的；如果大量查询是按操作人，那按时间分表反而每张表都要扫。**分表键选错，后面所有优化都是补救**。

**跨表事务不存在。** 分表之后写入是分片的，原来一个事务能保证的事现在保证不了。日志场景无所谓（写失败重试即可），但如果是有业务含义的数据，得想清楚补偿机制。

## 小结

分表本身不难，难的是**分完之后原来那些"顺手就能写"的查询全部要重写**。所以做决定之前先问自己：这张表的查询模式是什么？如果答案是"什么条件都可能查"，那可能不该分表，该做的是归档 —— 热数据留一张表，冷数据挪走。

这两个思路经常被混淆：**分表解决写入和存储，归档解决查询范围**。搞反了就会像我第一版那样，问题一个没少。
