「建了联合索引还是走全表扫描」「explain 里 key 是联合索引，但 rows 还是几十万」——这类问题几乎都能从索引结构上解释清楚：**联合索引是按列依次排序的字典，不是三个独立的索引拼在一起**。

## 联合索引的物理结构

`(a, b, c)` 的索引是一棵按 `a` 递增排的 B+ 树。`a` 相同的行，按 `b` 递增排；`b` 也相同的，按 `c` 递增排。叶子节点里存的是 `(a, b, c, 主键)`。

所以「能用索引」的前提是：**查询能确定一个连续的区间**。

```
a=1, b=2, c=3   → 精确定位到一个点          ✅ 三列全用到
a=1, b=2        → 定位到 (1,2,c) 的一段       ✅ 用到 a,b
a=1             → 定位到 (1,*,*) 的一大段     ✅ 用到 a
a=1, c=3        → (1,*,3) 在树里是分散的       ❌ c 用不上，只能靠过滤
b=2             → 完全无法定位起点             ❌ 索引失效
```

这解释了两件事：

1. **为什么必须从最左列开始**：只有前缀确定了，才能找到有序区间的起点。跳过 `a` 直接查 `b`，`b` 在整棵树里不单调。
2. **为什么 `(a,b,c)` 和 `(b,a,c)` 不一样**：索引列的顺序就是排序的优先级，不能任意换。

## 范围查询为什么会截断

假设有 SQL：

```sql
EXPLAIN SELECT * FROM t WHERE a = 1 AND b > 10 AND c = 5;
```

索引是 `(a, b, c)`。走一遍逻辑：

- `a = 1` → 定位到 `a=1` 的连续区间
- `b > 10` → 在这个区间内，`b` 是有序的，可以二分成 `b > 10` 的后半段。**得到一段连续区间**
- `c = 5` → 问题来了：在这段区间里，`b` 已经各不相同，`c` 在每个 `b` 值内部才有序。`c=5` 无法再收缩成一个连续区间

所以 `c` 这一列**不能用来定位区间**，只能逐行判断。`explain` 里 `key_len` 只覆盖到 `b`（含），`ref` 是 `const` 加一段范围。

**这就是「范围查询右边的列失效」的真正含义**——不是索引坏了，是 B+ 树的有序性在范围之后断掉了。

注意两个例外：

- `a IN (1, 2)` 虽然看起来是范围，但等价于多次等值查找，**不会**截断后续列
- `a = 1 AND b LIKE 'x%'` 前缀匹配可以截断，`LIKE '%x'` 直接失效

## 索引下推（ICP）补回来一部分

MySQL 5.6 之后有 `Using index condition`：

```
Extra: Using index condition
```

它的作用是：把 `c = 5` 的判断**下推到存储引擎层**，在索引上就地过滤，而不是把整段 `a=1 AND b>10` 的行全部回表再让 Server 层判断。

区别很实际：

| | 没有 ICP | 有 ICP |
| --- | --- | --- |
| 回表次数 | `a=1 AND b>10` 的所有行 | 满足 `c=5` 的行 |
| `EXPLAIN` Extra | — | `Using index condition` |

但 ICP 只能**减少回表**，不能减少扫描的索引条目。如果 `b>10` 匹配了 10 万行而 `c=5` 只有 100 行，ICP 还是得把那 10 万条索引读一遍。

## 怎么排索引列的顺序

三条规则，按重要性：

**1. 等值条件在前，范围条件在后。**

```sql
-- 查询模式：WHERE a = ? AND b = ? AND c > ?
-- 索引：(a, b, c)   ✅ 三列全用上
-- 索引：(a, c, b)   ❌ c 是范围，b 就废了
```

**2. 基数高的（区分度大的）放前面。** 这条常被过度强调。实际上如果前几列都是等值条件，顺序对查找效率影响很小（都是精确定位）。真正影响的是**能省掉多少列**：把区分度高的放前面，最左前缀就能更快缩小范围。

**3. 把最常用的查询模式作为前缀。** 索引 `(a, b)` 支持 `WHERE a = ?`、`WHERE a = ? AND b = ?`，但不支持单独 `WHERE b = ?`。所以先定「最高频的等值条件组合」，把它做成最左前缀。

一个反例值得记住：

```sql
-- 两个索引是不是可以合成一个？
INDEX (a, b)
INDEX (a)
```

可以。`(a)` 是 `(a, b)` 的最左前缀，多余的。删掉它省空间、省写入开销。

## 覆盖索引：让回表消失

如果查询需要的列全在索引里，就不需要回表：

```sql
SELECT a, b FROM t WHERE a = 1;      -- 索引 (a,b,c) 覆盖了
```

`EXPLAIN` 的 `Extra` 会显示 `Using index`。注意跟 `Using index condition` 区分：

- `Using index`：覆盖索引，**不回表**
- `Using index condition`：索引下推，**还是要回表**，只是回得少了

两者不冲突，可能同时出现 `Using index`。

这也是 `SELECT *` 是坏习惯的根本原因之一：只要查了索引外的列，覆盖索引就没了。

## 一个真实的效果对比

```sql
-- 表 t 约 500 万行；索引 (a, b, c)
-- 数据分布：a=1 约 50 万行，其中 b>10 约 10 万，其中 c=5 约 200 行

EXPLAIN SELECT * FROM t WHERE a=1 AND b>10 AND c=5;
```

| 场景 | 扫描行数 | 回表次数 | Extra |
| --- | --- | --- | --- |
| 无 ICP | 10 万 | 10 万 | — |
| 有 ICP | 10 万 | 200 | Using index condition |
| 改成 `(a, c, b)` 索引 | 200 | 200 | 用到 a,c |

最后一行是重点：如果你的查询里 `c = 5` 的选择性远高于 `b > 10`，并且这是高频查询，**换个列顺序比开 ICP 有用得多**。代价是 `(a, b, c)` 原本支持的 `WHERE a=1 AND b>10` 独立查询会变成部分失效——需要权衡，必要时两个索引都留。

## 小结

- 联合索引是**按列依次排序**的字典，索引列顺序就是排序优先级，不能随便换
- 范围条件之后的有序性断了，右边的列只能逐行过滤，这是「最左前缀」的物理原因
- `IN` 是多次等值，不截断；`LIKE 'x%'` 截断；`LIKE '%x'` 直接失效
- 索引下推（ICP）减少回表，不减少扫描的索引条目
- 列顺序优先按「等值在前、范围在后」，再把高频等值组合做成最左前缀
- 覆盖索引（`Using index`）比 ICP 更有效，前提是别 `SELECT *`

判断一个索引有没有用，就问一句：**这个查询能不能确定索引里的一段连续区间？** 能，就有效；不能，再多的列也只是陪跑。
