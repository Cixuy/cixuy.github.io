分布式锁出问题时，现象往往是「锁没锁住」，但根因通常在**三个不同的时限**上。很多人只调了其中一个，另外两个还在默认值上互相打架。

## 三个时限分别是什么

| 时限 | 典型配置 | 作用 | 配错的后果 |
| --- | --- | --- | --- |
| 锁超时（leaseTime） | 30s 或 -1 | 锁多久没被主动释放就自动过期 | 太短：业务没做完锁就没了 |
| 看门狗续期 | 1/3 leaseTime | 定时把过期时间往后推 | 没开：锁照样会过期 |
| 业务超时 | 1s ~ 30s | 调用方等结果的时间 | 太短：请求失败，但锁还在 |
| 请求排队超时（waitTime） | 3s | 等锁的时间 | 太短：直接拒绝，锁没责任 |

关键点：**这四个量必须满足一个偏序关系**，否则总有窗口出问题。

```
waitTime  ≤  leaseTime
业务超时   <   leaseTime
续期间隔   =   leaseTime / 3
```

## Redisson 的默认行为：leaseTime = -1 才是「看门狗」

这是最容易误解的一点：

```java
// ① 不传 leaseTime → 走看门狗，默认 30s，每 10s 续一次
lock.lock();

// ② 传了 leaseTime → 看门狗不启用，到点必过期，不管业务有没有做完
lock.lock(10, TimeUnit.SECONDS);
```

很多人写成第 ② 种「为了防止死锁，我加个 10 秒超时」，结果业务偶尔耗时 12 秒，锁在第 10 秒就释放了，第二个请求进来，两个线程同时操作同一个资源——**加超时反而制造了并发 bug**。

正确的思路是反过来：**默认用看门狗（不传 leaseTime），让锁跟着业务走；只有在明确知道上游一定会在 N 秒内结束时，才显式传 leaseTime**。

看门狗不是万能的，它有两条前提：

1. **锁的持有线程还活着**。进程被 kill -9、OOM、容器被驱逐，看门狗线程直接没了，锁只能等 30 秒自然过期
2. **续期时锁还是自己的**。如果锁被别人抢走（比如网络分区导致原锁过期），续期会失败并抛 `IllegalMonitorStateException`——这时业务必须能感知并回滚，不能闷头往下跑

## 时间轴：配错的样子

假设 `leaseTime = 10s`，业务实际耗时 12s：

```
t=0    请求A lock(10s) 成功，锁过期时间 = t+10
t=10   锁自动过期（看门狗没开）
t=10   请求B lock() 成功，锁过期时间 = t+20
t=10+  请求A 还在改数据，请求B 也在改 → 数据错乱
t=12   请求A 执行完，unlock() → 抛异常：锁已经不属于自己
```

注意最后一行：A 的 `unlock()` 会失败。Redisson 的 `unlock` 会校验锁的持有者，不是自己的锁会抛异常。这个异常很容易被 `catch` 掉忽略，于是问题被掩盖——**看到 unlock 抛 IllegalMonitorStateException，就说明锁已经被抢走了，业务多半已经出错了**。

## 那个经典的「删除别人的锁」

手写 `SETNX` 版本时这个问题更直白：

```java
// ❌ 错误：判断和删除不是原子的
if (redis.get(key).equals(myId)) {
    redis.del(key);          // 这中间锁可能过期并被别人拿走
}
```

正确做法是用 Lua 保证原子：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

不过就算用了 Lua，也只是「不会删错人」，**不能解决「我的业务还在跑但锁已经过期」**。后者只能靠看门狗续期或合理设置 leaseTime 解决。

## 业务超时该配多久

业务超时（比如 `@Transactional(timeout=5)` 或 HTTP 客户端超时）应该**小于**锁的生命周期：

```
业务超时  <  leaseTime（有看门狗时是「业务超时 < 看门狗认为的存活期」）
```

原因很实在：如果业务超时报错返回了，但线程还在后台慢慢跑（有些框架会这样），锁却已经被释放，这时候的并发是最危险的——调用方以为失败了，实际副作用还会发生。

所以配合关系是：

- **业务超时** = 你愿意等多久 → 决定用户体验
- **leaseTime** = 最坏情况业务会跑多久 × 安全系数 → 决定锁的兜底时间
- **waitTime** = 排队时等锁多久 → 决定并发量下的拒绝率

一个可用的组合：

```java
// 等锁最多 3s，锁自带 30s 看门狗
boolean ok = lock.tryLock(3, TimeUnit.SECONDS);
if (!ok) {
    throw new BusyException("资源正忙");
}
try {
    // 业务超时设成 20s，确保在锁的兜底时间内完成
    return doBusinessWithTimeout(20);
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

`isHeldByCurrentThread()` 那层判断很重要：如果锁已经因为超时丢失，直接 `unlock` 会抛异常，把原本的业务异常盖掉，日志里就看不到真正的原因了。

## 小结

- `leaseTime = -1`（不传）才会启动看门狗；传了固定值就是「到点必过期」
- 「加个超时防死锁」是最常见的错误直觉，它真正带来的是锁提前释放导致的并发
- `unlock` 抛 `IllegalMonitorStateException` 是**锁已易主**的信号，不是可以忽略的噪音
- 业务超时必须小于锁的生命周期，否则「接口报错了但副作用还在跑」
- Lua 只能保证不删错别人，不解决「自己还在跑但锁没了」

最后一句：分布式锁的正确性**不依赖 Redis 的高可用**。如果你的业务不能容忍锁丢失，那它需要的是数据库行锁或 ZooKeeper 这类带一致性的方案，而不是调几个超时参数。
