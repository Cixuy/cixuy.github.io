ServerOps 这个运维系统最初是"一套 MySQL 打天下"：服务器、告警、规则、指标，全塞进关系库。前两周跑得很好，问题是在第三个月暴露的。

## MySQL 是什么时候开始撑不住的

算一笔账：假设 50 台机器，每台 30 个指标，采集周期 5 秒。

```
50 × 30 × (86400 / 5) ≈ 2592 万行 / 天
```

一个月七亿多行。这张表很快出现三个症状：

1. **写入开始抖**。指标是批量 insert，单表索引维护成本随数据量线性上升，高峰期写入延迟明显。
2. **时间范围聚合变慢**。"最近 24 小时 CPU 趋势"这种查询要做 `WHERE time BETWEEN ... GROUP BY 5min`，在没有覆盖索引的情况下基本是全表扫。
3. **删除历史数据很痛**。`DELETE FROM metric WHERE time < ...` 会锁大量行、产生巨量 undo，跑一次能把主从延迟拉到几分钟。

第 3 点是最要命的 —— 指标数据 99% 的价值在最近两周，老数据必须清，但 MySQL 清数据的方式不适合这个模式。

## 为什么时序库处理这类场景更自然

时序数据库的几个设计前提正好对上指标数据：

- 写入是**追加**为主，几乎不更新
- 查询总是**按时间范围** + 按维度聚合
- 数据有明确的生命周期，**过期就该自动消失**

InfluxDB 在这三点上都是原生支持：按时间分区存储、`aggregateWindow` 直接在窗口上聚合、retention policy 自动过期。特别是最后一条，把"手动清数据"这个运维负担直接消掉了。

所以我最终的分工是：

- **MySQL** 存业务数据：服务器台账、用户、告警事件、自愈规则 —— 有关系、要事务、要 join
- **InfluxDB** 存指标：CPU、内存、磁盘、网络 —— 只追加、按时间查、会过期

## 坑一：把高基数字段做成了 tag

这是新手最容易犯的错，而且后果很严重。

InfluxDB 的 `tag` 是索引字段，每个 tag 值的组合会形成一条独立的 series。**series 数量爆炸，内存直接被吃光。**

我当时把一个本该是 field 的东西写成了 tag：采集批次 ID。每批数据都不一样，等于每 5 秒新增几百个 series，跑了一天内存就满了。

判断标准很简单：

| | tag | field |
|---|---|---|
| 用来做什么 | `WHERE` 过滤、`GROUP BY` | 数值计算、聚合 |
| 值的特点 | 基数低、可枚举 | 可以是任意值 |
| 典型例子 | 机器 ID、机房、指标名 | CPU 使用率、内存字节数 |
| 绝对不能放 | 时间戳、请求 ID、PID、UUID | —— |

写进去之前先问一句：**这个字段的取值能不能列出来？** 列不出来就放 field。

## 坑二：`aggregateWindow` 的窗口边界

查"最近一小时 CPU 均值，5 分钟一个点"：

```flux
from(bucket: "metrics")
  |> range(start: -1h)
  |> filter(fn: (r) => r._measurement == "cpu" and r._field == "usage")
  |> aggregateWindow(every: 5m, fn: mean, createEmpty: false)
```

两个参数值得注意：

- `createEmpty: false`：默认是 `true`，会把没有数据的窗口补成空行，前端画图会出现断点或者 0 值，看起来像"机器挂了"。设成 `false` 才是"没数据就不画"。
- 窗口是**按时间戳对齐**的，不是从你查询的起点开始切。所以"最近 1 小时"的首尾两个窗口可能是不完整的，算出来的均值会偏。如果对趋势判断敏感，查询范围要比展示范围多取一个窗口，画图时再裁掉。

## 坑三：保留策略比手动清理靠谱得多

一开始我写了个定时任务，每天删 30 天前的数据。后来发现两件事：一是删除本身很慢，二是**删完之后磁盘并不会立刻释放**（底层 compaction 需要时间）。

换成 bucket 级别的 retention 之后，删除变成了元数据操作，数据到期自动淘汰，磁盘空间由后台任务回收，代码里那几百行清理逻辑全部删掉。

```bash
# 30 天自动过期
influx bucket create -n metrics -r 720h
```

如果不同指标的生命周期不一样（原始数据留 7 天，聚合后的小时级数据留一年），建两个 bucket 分开写，不要挤在一个里面。

## 最后的选择建议

不是所有项目都需要上时序库。我的判断顺序是：

1. **数据量小、查询简单** → MySQL 就够，别为了技术栈好看引入新组件
2. **写入频繁但只查最近几天** → 先考虑 MySQL 分区表 + 定期 drop partition（比 delete 快几个数量级）
3. **写入量大 + 按时间聚合 + 需要自动过期** → 上时序库，收益明显

另外补一句：引入第二个存储之后，**一致性就是你要自己扛的事了**。MySQL 里删了一台服务器，InfluxDB 里它的历史指标还在 —— 要么接受这个不一致（大多数监控场景可以接受），要么在业务层做级联清理。这个成本在选型时容易被忽略。
