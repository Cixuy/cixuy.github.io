刚开始我以为"Agent"是个框架问题：装个 LangChain 或者 Spring AI，写几个 Tool 注解，就算接入了。

真做起来才发现，框架只是把这个循环包了一层。理解不了循环本身，出了事完全不知道从哪查——模型为什么又调了一次同样的工具、为什么明明查到数据却说没查到、为什么第六轮之后开始胡编。

## 循环本身没有魔法

一次普通的大模型请求是：给消息，拿回答。Agent 的差别只有一条：模型可以选择"我不回答，我先要一个工具的执行结果"。

于是整个系统就是一段循环：

```text
messages = [system, user]

for step in 1..max_steps:
    resp = model(messages, tools)

    if resp.stop_reason != "tool_call":
        return resp.text            # 模型决定回答，结束

    for call in resp.tool_calls:
        result = run(call.name, call.args)
        messages.append(tool_result(call.id, result))
```

真实代码里 `run()` 是一个按名字分发的 map，`tool_result` 是一条 `role: "tool"` 的消息，带上调用 ID 与结果文本。模型下一轮看到的就是"我要的东西回来了"，然后决定继续要还是收尾。

没有状态机，没有规划器，没有反思。所谓 Agent 能力，全都长在这段循环和每个工具的返回值上。

## 我给评审服务暴露了 6 个工具

做代码评审的时候，工具不是越多越好，而是要让模型能"自己决定去看什么"：

| 工具 | 作用 |
|---|---|
| `review_code` | 对一段代码跑规则，返回问题清单 |
| `search_similar` | 检索历史上相似问题 |
| `get_memory` / `set_memory` | 读写项目级规则（比如"忽略某条规则"） |
| `list_rules` | 列出当前生效的规则 |
| `explain_rule` | 解释某条规则为什么存在 |

这里有个反直觉的点：**`review_code` 一次就能把问题全列出来，为什么还要给检索和记忆？**

因为评审结论要能说服人。只报"第 12 行命名不规范"没用，得能补一句"这个项目历史上出现过三次同类问题，最近一次在 9 月"。证据靠检索拿，规则偏好靠记忆拿，这两件事模型自己判断不了要不要，必须做成工具让它自己决定调不调。

## 第一版漏掉的四个细节

### 1. 没有上限，循环停不下来

第一版 `while true`，靠模型自己收敛。结果遇到一个输入，模型连续四轮调 `search_similar`，每次都换关键词，每次都拿回一堆相似度不高的片段，越查越糊。

必须给两条硬约束：

- `max_steps`：超过就强制收尾，把已有结论直接返回，并标注"未完成全部检查"
- 同一个工具 + 同一组参数，第二次调用直接返回缓存结果，并附一句"该查询已执行过"

第二条比第一条有用得多。模型在循环里最容易犯的错就是重复劳动，把重复结果原样还给它，它自己就会换路子。

### 2. 工具返回的东西必须截断

`search_similar` 一开始返回完整片段，一次召回 8 段、每段上千字，第二轮就把上下文撑满了，模型开始丢前面的指令。

后来改成：每段只回前 200 字 + 相似度分数 + 片段 ID，如果模型想看细节，再用 ID 调一次 `read_chunk`。把"看什么"的决定权交回给模型，而不是一次性灌满。

### 3. 工具报错不能抛异常

工具内部抛异常，整个请求就断了，模型完全不知道发生了什么。正确的做法是把错误当成一次正常观测：

```json
{ "ok": false, "error": "review_code 超时（3000ms），静态分析服务可能没起来", "hint": "可以先用本地规则跑一遍" }
```

模型看到这段，通常会自己降级——换个工具、或者直接基于已有信息作答。抛异常等于把决策权从模型手里拿走，而这恰恰是 Agent 的价值所在。

### 4. 并行调用是批量的，不是并发的

模型一次可能返回多个 `tool_call`。我一开始顺序执行，一个个等，一个 800ms 的工具调用三次就是 2.4 秒。

其实同一轮里的多个调用之间通常没有依赖（模型是同时想出来的），可以并发执行再按顺序拼回结果。要注意的是：**同一个轮次里如果两个工具写同一份状态，就不能并发**。我的 `set_memory` 是写库，所以按工具名做了个白名单，只允许只读工具并行。

## 这一章的一句话总结

Agent 的能力上限由三件事决定：工具设计得好不好、返回值裁得够不够、错误喂得对不对。框架换哪个都一样，这三件事不变。
